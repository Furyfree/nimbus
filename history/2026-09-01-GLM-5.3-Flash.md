# GLM-5.3-Flash: a response to the FABLE design

Written 2026-09-01 against `nimbus` at `a5ea4d3`, `dotfiles` at `522584c`, and
the untracked `FABLE.md` proposal. It is a response record, not an accepted
contract. Nothing in `SPEC.md`, `CLI.md`, or `ROADMAP.md` changed to write it.
Verdicts below are recommendations to accept or reject one row at a time,
using FABLE's own section-8 convention.

## 1. Position

FABLE is the strongest challenge the design has received. Its central
proposal - moving definitions from the Nimbus binary into the workstation
repository - is right, and it must be decided before Phase 1 freezes TOML
types, because it changes what the resolver loads and what receipts record.
Roughly half of its section-8 rows should be accepted, two need rework, one
is rejected with a proof, and its housekeeping section contains stale claims.

## 2. Verdicts on the section-8 decisions, one row at a time

### Row 1: definitions embedded in the binary -> definitions in the workstation repository

Accept, with conditions. This is the most valuable row.

The embedded model's real cost is iteration speed: adding one package
requires a Go release, a COPR build, and `dnf upgrade` on every machine
before `nimbus plan` sees it. That tax lands on every learning iteration.
The escape hatch in `packages` proves the pain is already felt.

One correction to FABLE's framing: "nobody else can use Nimbus" is not the
deciding argument, because `SPEC.md` explicitly promises no generic
installer. The iteration-speed argument alone justifies the row.

The Terraform shape - generic engine, versioned schema, personal
configuration repository, state - is proven, and Chezmoi already proves it
for `$HOME`. The checkout already holds `machines/`; `nimbus/` beside it is
coherent, and the single-clone bootstrap is already built around one
checkout.

Receipts improve under this model: checkout commit, dirty flag, and the
SHA-256 of the canonical `nimbus/` tree are strictly more precise per machine
than a release digest. Keep the Nimbus version and the RPM signature as the
engine's own provenance.

Conditions that come with acceptance:

- The engine becomes a schema-range interpreter. `nimbus/nimbus.toml` needs
  `schema` and `min_nimbus`, validated the way Ignition's spec support table
  works (D2 in the first analysis).
- The trust anchor for definitions moves from RPM signing to the checkout
  commit. The engine itself stays RPM-signed.
- `nimbus validate` becomes the workstation repository's CI gate.
- One detail FABLE misses: the `init --new` example tree must be embedded in
  the binary as bootstrap seed data. That is a small, acceptable return of
  embedding, because it is never resolved as live definitions.

Timing: cheap now, expensive after Phase 1 fixtures exist. Decide
immediately.

### Row 2: `machine.toml` symlink -> `config.toml` with `checkout` and `machine`

Accept outright. Explicit keys are printable, JSON-serializable, overridable
with `--checkout` and `--machine`, and cannot dangle. It also dissolves the
plain-manifest-versus-link duality that `SPEC.md` currently carries for the
no-repository workflow.

### Row 3: three bootstrap flows -> one flow with `init --new`

Accept as a pair with row 2. One manifest location, and adoption becomes
`git remote add origin` plus `git push` - Git work the user already owns.
Two guards:

- The `git init` at init time must be printed, never silent. The
  no-silent-Git rule is about visibility, not about remote operations.
- The local repository is only fully functional offline if row 1 is also
  accepted, because the definitions must live in the checkout. This is a
  reason to take rows 1-3 as one decision package.

### Row 4: plus read-only `rev-parse HEAD` and `status --porcelain` for receipts

Accept. `SPEC.md`'s "exactly one Git read" needs rewording to "one network
Git operation - the init clone - plus read-only local `rev-parse` and
`status` for provenance". Still no fetch, commit, or push.

### Row 5: Mise, Cargo, and uv providers out; mise config as the single declaration

Accept. This is a real double-declaration flaw in the current roadmap.
`~/.config/mise/config.toml` is Chezmoi-managed and already declarative; a
Nimbus mise provider competing with it creates two owners for one intent -
the exact drift class the ownership split exists to prevent.

Consequences to accept honestly:

- The cargo-owned tools on this workstation (`just`, `watchexec`, `nirius`,
  `cargo-update`) must move under mise's cargo backend in the mise config,
  or stay cargo-managed and count as unmanaged. Pick one; this response
  recommends the mise backend.
- The dotfiles rule that scripts never install packages gains one documented
  exception: a `run_onchange_` script that hashes the mise config and runs
  `mise install`. User scope, no sudo, no DNF. Record it in the dotfiles
  `AGENTS.md`.
- Nimbus keeps installing `mise` itself through DNF in `common`; `nimbus
  status` may print `mise ls --missing` as a hint, nothing more.

### Row 6: seed `hyprland.lua` in `$HOME` -> system-owned seed session

Accept, and this supersedes the seed wording added at `a5ea4d3`. The
system-side design - `/usr/share/wayland-sessions/hyprland-seed.desktop`
with `Exec=Hyprland --config /usr/share/nimbus/seed/hyprland.lua` - removes
all three costs of the `$HOME` seed: the only-user-home-write exception, the
Chezmoi-managed-path check, and the yield semantics. It also resolves
FABLE 2.2.10's fair catch that nothing defines a "desktop selection" beyond
a profile: the seed becomes static system data. Bonus: it doubles as a
permanent recovery session for a broken user config, which the `$HOME` seed
cannot.

### Row 7: profile handoff plus `Machine=<id>`

Accept. It fills the gap the SPEC dropped - typed per-machine variables -
with Chezmoi-native data keyed by the manifest ID, with no Nimbus schema.
`.chezmoidata/machines.toml` is exactly where monitor layouts belong, and a
direct `chezmoi init` on another OS just answers or skips one prompt. The
contract test that `$machineChoices` matches the profile set belongs in CI
as a test, not as prose discipline.

### Row 8: `package_constraints` materialized as `dnf versionlock`

Accept. A constraint only the resolver sees is advisory: `topgrade` or a
plain `dnf upgrade` bypasses Nimbus and moves the pinned package. As planned
resources, constraints become system policy that survives every updater.
Phase it: `validate` rejects constraints until the provider can materialize
them. One interaction FABLE does not spell out: the `desktop-session` group
transaction must remove and reapply versionlocks inside its own transaction
so the grouped update can move within its reviewed window.

### Row 9: catalog entry per package -> catalog as exception list

Accept. Bare names default to DNF from enabled repositories, verified with
`rpm -q`; catalog files exist only for non-default source or lifecycle. This
matches the manifest escape hatch that already exists and deletes hundreds
of trivial files. Guardrails: golden tests must cover a bare-name
resolution so the default path stays deliberate, and a catalog entry remains
mandatory for anything with a foreign source, an update group, verify hooks,
or manual steps.

### Row 10: engine verbs only; conveniences move to `home/`

Mostly accept, with one boundary: privileged operations cannot move into
home-directory scripts. `launch browser|webapp` becomes Chezmoi-managed
scripts cleanly, since the keybinds already live there. `windows
start|stop|connect|purge-data` can move, with purge keeping its second
confirmation naming the path - but `windows setup` starts a privileged
container and stays a Nimbus command. The dashboard and TUI deferral is
already the stated plan; "every verb has stable `--json` first" is the right
gate and matches the envelope contract from the first analysis.

### Row 11: `postinstall` command -> `[[manual]]` entries surfaced by `status`

Accept. `[[manual]]` entries with check commands carry the same information
as the CLI.md postinstall list without a second interactive surface. The
postinstall residue mapping in the first analysis (MOK enrollment,
fingerprint, second-boot check, dotnet shim, `chezmoi diff/apply` review)
maps onto it directly. A dedicated command can return later if the list
grows.

### Row 12: recovery points before any disruptive or reboot step

Accept. It operationalizes the existing rule - recovery is defined before a
mutating resource is enabled - using the Btrfs subvolume layout already
documented in `FEDORA_TEST_INSTALLATION.md`, and records the recovery-point
ID in the receipt. Keep rollback as documented manual work first; `nimbus
rollback` arrives only after a VM drill, exactly as FABLE says.

### Row 13: bootstrap special-casing removed

Reject as written, with a proof of internal contradiction: FABLE 3.12 step 2
clones the checkout, which needs Git, and step 6 runs `chezmoi init`, which
needs Chezmoi - but its step 5 installs them "if missing" only during apply,
after both are already required. The bootstrap must install Nimbus, Chezmoi,
and Git before init can run; that ordering is structural, not a special case
to remove. What survives from the row: under row 1's generic-engine model,
Chezmoi and Git can be ordinary `common` catalog entries that apply adopts
like any package. Keep the bootstrap-plus-adoption design and treat the
bootstrap as "the minimal plan needed before init".

## 3. Corrections to FABLE's factual claims

- `hej.md` does not exist in the tree at `a5ea4d3` or later. The housekeeping
  item is stale or refers to an unsaved scratch file. Nothing to delete.
- "history/GLM-5.3-Flash.md largely folded in" is correct: the remaining
  live items are the desktop-session group analysis and the two publication
  actions, both already tracked in `OPEN_QUESTIONS.md`.
- The profile-vocabulary duplication (FABLE 2.2.2) was fixed in dotfiles
  commits `2c14046` and `522584c`: the template now consumes
  `promptMultichoiceOnce` under the `Profiles` key. The discipline gap
  FABLE points at is real, which is why the row-7 contract test belongs in
  CI rather than in prose.
- FABLE 2.2.10's catch against the `a5ea4d3` seed wording is fair. Row 6's
  system-seed redesign dissolves the wording instead of defining the input.
- FABLE.md itself is untracked in this repository. If kept, the AGENTS.md
  rule puts dated analysis records in `history/`.

## 4. What FABLE adds beyond both earlier analyses

- The sudo line as one sentence (FABLE 3.3) is the best compression of the
  ownership matrix anywhere in the project. Adopt the wording even where
  the scope differs.
- The Chezmoi verb alignment (FABLE 3.2) is good naming guidance for the
  command surface.
- `status` comparing the last receipt's definitions digest with the checkout
  is the cheapest possible "is there unapplied configuration" answer, with
  no inspection.
- Section 5's invariants-as-tests are directly adoptable into `just check`:
  a sandbox-home write assertion, a no-package-names-in-Go-branches grep,
  and a fake-runner assertion that read-only commands never exec `sudo`.
- The `__step` re-exec (FABLE 3.7) is the first concrete mechanism for the
  operation-scoped privileged step. Requirements before acceptance: a
  root-owned plans directory, per-step re-verification of the file hash
  against the argv digest to close the TOCTOU window, and per-step atomic
  receipts. FABLE states all three; they must become tests, not prose.

## 5. What FABLE does not cover

- The Fedora correctness set from the first analysis (rpmnew/rpmsave
  reporting, `rpm -V` verification, invoking-user resolution under sudo,
  DNF5 parsing churn, libvirt and firewall coexistence, locale and keymap)
  remains necessary under FABLE's model. The nvidia component example
  carries the Secure Boot MOK manual step, which is right.
- Under row 1, reproducibility across machines becomes per-commit rather
  than per-release. That is acceptable, but the support table between
  definition schemas and engine releases becomes a hard requirement, not a
  nice-to-have.

## 6. Decision package

Decide now, before Phase 1 freezes TOML types - cheap now, expensive after:
rows 1, 2, 3, 5, 6, 7, 8, and 9.

Defer to their phases: row 4 with the first receipts, rows 10 and 11 with
the command surface, row 12 with the first mutating provider.

Reject: row 13.

If accepted, execute FABLE 9's coordinated update in one change: `SPEC.md`,
`CLI.md`, and `ROADMAP.md` here; `PROFILES.md`, `AGENTS.md`, and the
`machines/` docs in the dotfiles repository; then move `FABLE.md` to
`history/` or shrink it to a design record. Until that acceptance, no
contract file changes.
