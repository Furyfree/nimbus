# Response to FABLE

Written 2026-09-01 after reviewing `FABLE.md` against Nimbus at `a5ea4d3`
and the dotfiles repository at `522584c`.

## Conclusion

`FABLE.md` is a useful decision paper, but it should not be accepted as a
replacement architecture.

Its strongest proposals remove genuine ownership overlap: use a system-owned
recovery session instead of a seed file under `$HOME`, pass a machine ID to
Chezmoi, make version constraints effective outside Nimbus, simplify ordinary
DNF package declarations, and keep the first implementation focused on the
resolver and engine verbs.

Its central proposal is different. Moving all definitions into the dotfiles
checkout changes Nimbus from the owner's versioned workstation manager into a
generic privileged engine that executes a repository's data. That is a valid
product direction, but it is not a correction to the accepted contract. The
current contract explicitly builds for the owner's workstations first and
does not promise a generic engine. The move also introduces a privileged-input
trust boundary, schema compatibility across two repositories, bootstrap
cycles, and new Git dependencies that FABLE does not resolve.

The right response is therefore:

1. Keep the Phase 1 outcome and embedded-definition model.
2. Accept the small independent corrections that improve ownership.
3. Defer generic external definitions until a separate product decision,
   informed by an implemented resolver and real release friction.
4. Do not adopt FABLE's execution protocol, Terraform-shaped command surface,
   or bootstrap rewrite as part of Phase 1.

## What the current repositories actually establish

The current foundation is internally consistent on the points that matter for
Phase 1:

- Nimbus owns system intent and Chezmoi owns user files.
- The four machine profile IDs are `common`, `development`, `gaming`, and
  `hyprland-noctalia` in both repositories.
- The dotfiles template already consumes `Profiles` with
  `promptMultichoiceOnce`.
- The 1Password choice no longer depends on the `op` binary being installed.
- `machines/` already exists in the dotfiles repository.
- Phase 1 is read-only and deliberately excludes Bubble Tea.

The profile list is still duplicated in the Nimbus definitions and the
Chezmoi prompt choices, so drift remains possible. It is not currently out of
sync, however. FABLE's proposed contract test detects duplication rather than
removing it.

`hej.md` does not exist in either reviewed repository at the stated commits,
so its deletion is not a valid housekeeping item.

## Problems in FABLE's model

### Genericity is an unaccepted requirement

FABLE treats "usable by others without a fork" as a requirement and then uses
it to prove that embedded definitions are wrong. `SPEC.md` says something
narrower: Nimbus is built first for the owner's machines, while others may
inspect or adapt it.

Embedded definitions do have a release cost, but they also give an installed
binary a reviewed, packaged, immutable definition set. During development the
accepted design already loads edited files from the working tree, so learning
and resolver iteration do not require a COPR release for every edit. Release
friction should be measured after the resolver exists, not assumed before it.

External definitions can be reconsidered if Nimbus intentionally becomes a
generic engine. That decision would need an explicit trust and compatibility
contract, not only a layout change.

### Privilege is not an ownership model

The sentence "if applying it needs `sudo`, it is Nimbus" is attractive but
too weak. Ownership is determined by desired-state authority and lifecycle,
not by the privilege bit.

User-scoped runtimes, Cargo tools, user Flatpaks, rootless containers, and user
services may not need `sudo`, but they still need one declarative owner,
inspection, verification, update, and removal behavior. Conversely, Chezmoi
may render a user-owned file whose effect is later consumed by a separate
tool. The file owner and the resource lifecycle owner are not necessarily the
same thing.

Moving tool declarations into a Chezmoi-managed Mise file can be coherent if
Mise is explicitly the lifecycle owner and the user runs `mise install`.
Adding a Chezmoi `run_onchange_` installer is not a harmless detail: it changes
the dotfiles repository's current rule that scripts do not install packages.
That contract should not be weakened indirectly.

### External definitions are privileged input

In FABLE, the workstation repository may provide root-owned files and trigger
argv that Nimbus runs with `sudo`. Those definitions are not merely passive
data; they are privileged executable input.

Before such a model could be accepted, it would need at least:

- an explicit repository trust decision during init and after origin changes
- schema-to-engine compatibility rules and a supported migration policy
- canonical hashing that includes file content, modes, links, and definition
  data while rejecting path traversal and symlink escapes
- exact plan rendering for privileged argv and every root-owned file diff
- rules for dirty checkouts and for changes made by Chezmoi's Git lifecycle
- CI that validates the workstation repository with a compatible Nimbus
  version

A commit ID is not "strictly more precise" than the current embedded digest.
For a dirty checkout, only a canonical tree digest identifies the input. A
commit, dirty flag, and tree digest can be equally precise, but the external
model is not inherently more reproducible than a versioned binary with an
embedded-definition digest.

### The proposed profile test couples the wrong layers

Having Nimbus parse `$machineChoices` from a Go template makes the generic
system engine understand a Chezmoi implementation detail. It also leaves two
lists to maintain.

If external definitions are ever accepted, profile IDs should come from one
canonical, tool-neutral data source, with any Chezmoi choice list generated or
validated by repository-local tooling. In the current embedded model, a small
cross-repository contract test is sufficient, but it should not become part of
the Nimbus runtime CLI.

### The bootstrap simplification contains a cycle

FABLE makes Git an ordinary `common` catalog entry, but `nimbus init REPO`
needs Git before it can clone the repository containing that catalog. The
`--new` path also needs Git before it can run `git init`. Git therefore remains
a bootstrap prerequisite unless Nimbus adds a separate archive transport,
which would be more machinery rather than less.

Chezmoi can become an ordinary planned package because it is not needed until
the handoff. Git cannot. Nimbus also cannot sensibly manage its own initial
installation through definitions that are unavailable until after Nimbus is
installed.

The three user stories can share one internal state machine without pretending
they have identical ownership:

- fresh repository clone
- restoration from an existing tracked manifest
- local configuration without a repository

Creating a new Git repository is a useful optional workflow, not a necessary
replacement for the local-manifest flow.

### The `$HOME` invariant is internally inconsistent

FABLE says Nimbus writes below `$HOME` only in `~/.config/nimbus` and
`~/.cache/nimbus`, then has `nimbus init` clone or create
`~/.local/share/chezmoi`, write `machines/<id>.toml`, and invoke `chezmoi init`,
which writes Chezmoi configuration.

The useful invariant is narrower: outside an explicitly reviewed bootstrap
checkout and Nimbus' own XDG state, Nimbus does not manage user targets.
Chezmoi remains the only engine that applies home-directory configuration.

### The execution protocol contradicts the accepted privilege rule

The accepted contract runs each privileged native command directly through
`sudo`. FABLE instead runs `sudo nimbus __step ...`, which turns Nimbus into a
privileged plan executor that launches the native command. That is a real
security and implementation change, but section 8 does not list it.

It also leaves unanswered how the root-owned plan is staged, how a user-provided
plan file becomes the root-owned canonical plan, how stale facts are rejected,
and how partial receipts relate to a later receipt-writing step.

Phase 3 should begin with direct native commands as specified. A privileged
internal operation may be justified for atomic receipt or file writes, but a
general `__step` executor should be introduced only after its threat model and
need are demonstrated.

### Several Terraform features are premature

`apply FILE`, `--target`, `--reinstall`, `forget`, moved-resource metadata, and
automatic recovery points all add state semantics before Nimbus has one DNF
provider.

In particular, `--target` can bypass coordinated update groups or leave a
dependent graph partially reconciled. Terraform itself treats targeted plans
as exceptional recovery tools, not the normal "just install this" path.
Nimbus should not promise that behavior until dependency closure, receipts,
and recovery have been proven.

The Terraform analogy is useful for separating desired, observed, and applied
state. It should not determine the command surface.

### `status` must not stop inspecting drift

Comparing the current definition digest with the last receipt is a useful fast
check for changed intent. It does not answer whether the system drifted.
The accepted `status` contract covers desired, observed, and last-applied
state. A fast configuration-digest indication can be added, but it must not
replace inspection while still claiming complete status.

## Decision register

The following decisions should be applied independently rather than accepting
section 8 as a bundle.

| FABLE proposal | Response | Reason |
|---|---|---|
| Move definitions to the workstation repository | Reject for Phase 1; revisit as a product decision | It changes Nimbus into a generic privileged engine and needs a trust, schema, and compatibility design. |
| Replace the manifest symlink with `config.toml` | Keep the symlink for the accepted model | The extra checkout key is needed mainly by the rejected external-definition model. A dangling link is visible and diagnosable. |
| Replace the local-manifest flow with `init --new` | Keep the local flow; consider `--new` later | A local Git repository is useful for some users but does not remove the bootstrap distinctions or the Git prerequisite. |
| Permit local read-only Git inspection | Accept as a clarification | `rev-parse` and `status --porcelain` can support provenance and warnings without fetch, commit, pull, or push. Network Git operations remain explicit. |
| Move Mise, Cargo, and uv ownership out of Nimbus | Defer and decide per lifecycle | Consolidation under Mise may reduce providers, but a Chezmoi install script conflicts with current ownership rules. |
| Replace the home seed file with a system seed session | Accept, subject to a VM proof | It removes the only managed user-file overlap and gives a durable recovery session. Verify the greeter entry, absolute config path, and removal behavior. |
| Add `Machine=<id>` to the Chezmoi handoff | Accept | It supplies stable, non-secret per-machine user data without making Nimbus a template engine. Define direct-init and missing-ID behavior. |
| Materialize package constraints | Accept the invariant, not yet the mechanism | Constraints must affect native updates. Prove how each provider represents ranges; do not assume DNF versionlock can preserve Nimbus syntax losslessly. |
| Make catalog entries exceptions rather than one file per package | Accept for provider-default resources | A bare Fedora package can use a typed DNF default lifecycle. Non-default source, verification, update group, artifact, or removal behavior still requires catalog data. |
| Remove the dashboard and package browser | Keep out of the current phase | This is already true in `ROADMAP.md`. Long-term UI is a product choice and can remain a thin view over stable JSON commands. |
| Move `windows` and `launch` helpers out of Nimbus | Split the answer | Move personal launch helpers to Chezmoi. Keep declarative Windows host resources in Nimbus; defer daily runtime helpers until their owner and recovery behavior are clear. |
| Replace `postinstall` with manual entries in `status` | Defer UI; accept one underlying model | Stable typed manual tasks with checks are useful. Whether they have a dedicated view or appear in status should not create two state models. |
| Take recovery points before disruptive work | Accept as a Phase 3 requirement | Classify recovery per transaction or resource group, not blindly per step, and enable it only after a restore drill and retention policy exist. |
| Make Chezmoi and Git ordinary catalog entries | Accept only for Chezmoi | Git is required to obtain the catalog and remains bootstrap infrastructure. |

## Recommended bounded follow-up

No architecture rewrite is needed before Phase 1. If these decisions are
later authorized, the smallest coherent documentation change would be:

1. Replace the home seed-file contract with a system-owned seed session in
   `SPEC.md`, `CLI.md`, and `ROADMAP.md`, with VM validation and recovery.
2. Add the machine ID to the Chezmoi handoff and define its direct-init
   fallback in both repositories.
3. Clarify that local read-only Git inspection is allowed while network and
   mutating Git operations remain forbidden.
4. Define provider-default DNF package semantics before the Phase 1 catalog
   types are frozen.
5. Record materialized constraints as an unresolved provider question until
   DNF5 behavior is verified.

That is one bounded contract-reconciliation phase. It should stop before Go
implementation, package changes, bootstrap changes, or any system mutation.

The generic-engine question should remain separate: decide first whether
"others can use Nimbus without forking its definitions" is an accepted product
outcome. Only a yes justifies redesigning definition loading, repository trust,
configuration location, receipts, and bootstrap around an external
workstation repository.
