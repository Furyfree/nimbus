# FABLE: a design for Nimbus and the dotfiles repository

Written 2026-09-01 against `nimbus` at `a5ea4d3`, `dotfiles` at `522584c`,
and `docs/setup` as history. It is a design proposal, not an accepted
contract. Where it disagrees with `SPEC.md`, `CLI.md`, or `ROADMAP.md`, the
disagreement is listed in section 8 so it can be accepted or rejected one
item at a time.

## 1. What you are building

One Git repository describes a workstation. Two engines apply it. Nimbus
applies the part that needs `sudo`. Chezmoi applies the part under `$HOME`.
Both are plan-first, both keep the native tools visible, and either one works
when the other is missing.

```text
        workstation repository (one checkout: ~/.local/share/chezmoi)
        +------------------------------------------------------------+
        |  machines/<id>.toml   which profiles this machine selects   |
        |  nimbus/              system definitions (data, not code)   |
        |  home/                Chezmoi source state (.chezmoiroot)   |
        +------------------------------------------------------------+
                 |                                     |
        nimbus (Go engine)                    chezmoi (unchanged)
        runs as you, sudo per step            runs as you, never sudo
                 |                                     |
        validate -> plan -> apply             init -> diff -> apply
        receipts in /var/lib/nimbus           state in ~/.config/chezmoi
                 |                                     ^
                 +-- chezmoi init --promptMultichoice Profiles=...
                                  --promptString Machine=<id>
```

The one structural change this document makes is where the system
definitions live. Today `profiles/`, `components/`, and `catalog/` are
planned as TOML embedded in the Nimbus binary. This design moves them into
the same repository that already holds `machines/` and `home/`. Nimbus then
becomes what Terraform and Chezmoi already are: a generic engine over a
personal repository. Everything else follows from that.

## 2. Assessment of the current plan

### 2.1 What is right and should not move

- The ownership split is the best part of the plan. System state to Nimbus,
  user files to Chezmoi, secrets to 1Password, nothing in the middle.
- Plan before apply, receipts with provenance, the approved-plan digest,
  explicit prune, no root daemon, no sudo keepalive, no silent Git.
- Chezmoi is invoked as Chezmoi. No wrapper, no `--apply`, no shadow tree.
  The fleek post-mortem in `history/` is the right warning.
- Machine manifests live in the dotfiles checkout, outside the Chezmoi source
  root, and Nimbus never commits them.
- Read-only first. A resolver with golden tests is the right first Go task
  for someone learning Go.
- The dotfiles scaffold is disciplined: `.chezmoiroot`, canonical templates
  with one-line platform wrappers, placeholders ignored until reviewed,
  scripts forbidden from touching the system.

### 2.2 Where it strains

1. **Embedded definitions make Nimbus personal by construction.** Adding a
   package to the `development` profile requires a Go release, a COPR build,
   and `dnf upgrade` on every machine before `nimbus plan` sees it. Nobody
   else can use Nimbus without forking the Go repository. The `packages`
   escape hatch in the manifest proves the pain is already felt. This is the
   one decision that blocks "usable by others" and it also slows your own
   iteration while learning Go.

2. **The profile vocabulary is duplicated by hand.** The profile IDs exist in
   Nimbus TOML and again as `$machineChoices` in `.chezmoi.toml.tmpl`, with
   nothing but discipline keeping them equal. The GLM review found them out
   of sync once already.

3. **The handoff carries profiles but not identity.** Per-machine user data
   such as monitor layout has no home. `docs/setup` proposed typed variables
   through Nimbus; the current SPEC dropped them without a replacement.
   Chezmoi already solves this with `.chezmoidata` keyed by a name. It only
   needs the machine ID.

4. **User-scope package managers are double-declared.** The roadmap gives
   Nimbus Mise, Cargo, and uv providers. But `~/.config/mise/config.toml` is
   a Chezmoi-managed file that is itself a declarative tool list. Two owners
   for the same intent is the exact drift the ownership split exists to
   prevent.

5. **The seed `hyprland.lua` breaks the cleanest rule you have.** It is the
   only `$HOME` write Nimbus performs, it needs a "does Chezmoi manage this
   path" check, and it needs yield semantics. Hyprland accepts `--config`,
   so the seed can be a system-owned session entry instead and the rule
   "Nimbus never writes user files" becomes absolute.

6. **Version constraints are fiction unless materialized.** `topgrade` is a
   Chezmoi-managed config that runs `sudo dnf upgrade`. A constraint that
   lives only in Nimbus's resolver is bypassed the first time anyone updates
   without Nimbus. Constraints must land in `dnf versionlock` or not exist.

7. **`CLI.md` describes a product, not an engine.** A Bubble Tea dashboard,
   a fuzzy package browser, `windows start|stop|connect`, and `launch
   browser|webapp` are all user-facing conveniences that do not manage state.
   For one person learning Go they are the scope risk, and for others they
   are personal.

8. **Three bootstrap flows where one would do.** Fresh, reinstall, and
   no-repository each have their own manifest location, link semantics, and
   adoption story. If the no-repository flow simply creates a local
   repository, all three become one flow with one difference: whether
   `origin` exists yet.

9. **Recovery points are designed in `FEDORA_TEST_INSTALLATION.md` and
   almost absent from `SPEC.md`.** The Btrfs subvolume layout is the best
   recovery primitive you have and the apply model barely references it.

10. **Small drift.** `hej.md` contains a pasted prompt and should go.
    `history/GLM-5.3-Flash.md` is largely folded in. `SPEC.md` says
    "rendered from the machine's desktop selection" while nothing defines a
    desktop selection other than a profile.

## 3. The model

### 3.1 Three things, borrowed from Terraform

Terraform separates a generic binary, versioned providers, your configuration
in your repository, and state that records what the binary manages. Nimbus
should have the same four parts and nothing else.

| Terraform | Nimbus |
|---|---|
| `terraform` binary | the `nimbus` engine, one Go binary |
| providers | typed providers inside the engine: `dnf`, `copr`, `flatpak`, `systemd`, `file`, `boot` |
| root module and modules | machine manifest, profiles, components |
| variables and tfvars | `machines/<id>.toml` |
| data sources | facts from read-only inspection |
| resources | typed resources produced by resolution |
| state | receipts under `/var/lib/nimbus` |
| `plan -out` and `apply FILE` | `nimbus plan --out FILE` and `nimbus apply FILE` |
| `import` | adoption of an installed, desired, unowned resource |
| `-target` and `-replace` | `--target RESOURCE` and `--reinstall RESOURCE` |
| outputs and `terraform_remote_state` | the Chezmoi handoff |
| `.terraform.lock.hcl` | the definitions commit recorded in every receipt |
| workspaces | machines |
| `moved` blocks | `renamed_from` on a catalog entry |

What Nimbus deliberately does not borrow: remote state, a package lockfile,
and `destroy`. Fedora is the version authority for packages, and removal is
an edit to the manifest followed by a plan.

### 3.2 The same verbs as Chezmoi

Chezmoi already has the vocabulary users understand. Reuse it verbatim so
the two tools feel like one system.

| Chezmoi | Nimbus |
|---|---|
| source directory `home/` | `nimbus/` in the same checkout |
| `.chezmoiversion` | `nimbus/nimbus.toml` with `schema` and `min_nimbus` |
| `managed`, `unmanaged`, `status`, `diff`, `verify`, `doctor`, `forget` | same verbs, same meaning, applied to system resources |
| `.chezmoiexternal.toml` (url, sha256, refresh) | catalog `artifact` provider with the same fields |
| `run_onchange_` scripts | triggers, deduplicated per apply |
| `.chezmoidata/` | `machines/<id>.toml` for the system, `.chezmoidata/machines.toml` for the home |
| `chezmoi init --prompt` | `nimbus init` |

### 3.3 The sudo line

The ownership rule collapses to one sentence:

> If applying it needs `sudo`, it is Nimbus. If it lives under `$HOME`, it
> is Chezmoi or a tool that Chezmoi configures.

| Thing | Owner | Mechanism |
|---|---|---|
| repositories, RPMs, system Flatpaks | Nimbus | `dnf`, `flatpak --system` |
| `/etc` files, drop-ins, `modprobe.d`, sysctl | Nimbus | `file` provider with source under `nimbus/root/` |
| services, timers, greeter, portals, seed session | Nimbus | `systemd`, `file` |
| boot, kernel args, LUKS inspection, versionlock | Nimbus | `boot`, `dnf` |
| the Chezmoi binary and Git | Nimbus | catalog entries in `common` |
| `chezmoi init` with the resolved selection | Nimbus, once | handoff, section 3.10 |
| everything under `$HOME` | Chezmoi | source state |
| user-scope tools: runtimes, `cargo:`, `npm:`, `pipx:`, `go:` | mise | `~/.config/mise/config.toml`, Chezmoi-managed |
| user Flatpaks, if any | user or a Chezmoi `run_onchange_` script | `flatpak --user` |
| SSH config, agent keys | Chezmoi + 1Password | templates |
| credentials, caches, history, sessions | nobody | never tracked |

Two consequences:

- Nimbus writes under `$HOME` only in `~/.config/nimbus` and `~/.cache/nimbus`.
  Nothing else, ever, so there is no "does Chezmoi manage this path" logic.
- Nimbus has no user-scope provider family. Mise, Cargo, and uv leave the
  roadmap. Nimbus installs `mise` as a package; Chezmoi manages its config;
  mise reconciles its own tools. `nimbus status` may print
  `mise ls --missing` as a hint, nothing more.

### 3.4 The workstation repository

The dotfiles repository becomes the workstation repository. Renaming it is
optional; the layout is not.

```text
dotfiles/
  .chezmoiroot                 home
  .chezmoiversion              2.72.0
  home/                        Chezmoi source state, unchanged
    .chezmoi.toml.tmpl
    .chezmoidata/machines.toml per-machine user data, keyed by machine ID
    ...
  machines/                    already here; unchanged shape
    desktop.toml
    laptop.toml
  nimbus/                      moved from the Go repository
    nimbus.toml                schema = 1, min_nimbus = "0.1"
    profiles/*.toml
    components/*.toml
    catalog/*.toml
    triggers/*.toml
    root/                      sources for /etc and /usr files
      etc/brave/policies/managed/nimbus.json
      usr/share/wayland-sessions/hyprland-seed.desktop
      usr/share/nimbus/seed/hyprland.lua
```

Why the same repository and not a third one:

- One clone at bootstrap. `nimbus init` already clones it.
- `chezmoi update --apply=false` pulls system and user intent together, and
  `nimbus status` notices the definitions tree changed. One sync verb.
- The profile IDs are used within one repository, so a contract test can
  prove `.chezmoi.toml.tmpl` and `nimbus/profiles/` agree (section 3.10).
- macOS and Windows checkouts carry `nimbus/` harmlessly, exactly as they
  already carry `machines/`. `.chezmoiroot` keeps Chezmoi out of it.

The Nimbus Go repository keeps an `examples/` tree that mirrors this layout.
It is documentation and the seed for `nimbus init --new`, never resolved
directly by an installed engine.

Reproducibility does not weaken. Every receipt records the checkout commit,
a dirty flag, and the SHA-256 of the canonical `nimbus/` tree. "This machine
runs the definitions of release 0.4.1" becomes "this machine runs commit
`abc123`", which is strictly more precise and works per machine.

### 3.5 Definitions

Four layers, each answering one question. Keep them thin.

| Layer | Question | Analogy |
|---|---|---|
| catalog entry | how is this one package installed, verified, removed | provider resource |
| component | what does this capability need: packages, files, services, triggers, manual steps | module |
| profile | which components form a bundle | composition preset |
| machine | what does this box select on top of the bundles | tfvars, workspace |

**The catalog is the exception list, not a registry.** A package named in
a component or a manifest with no catalog file means `dnf` from enabled
repositories, verified by `rpm -q`. A catalog file exists only when something
is non-default. That removes hundreds of trivial files and keeps "no
package-specific Go" intact.

```toml
# nimbus/catalog/akmod-nvidia.toml
schema = 1
id = "akmod-nvidia"
provider = "dnf"
repo = "rpmfusion-nonfree"          # a component id that must be selected
update_group = "desktop-session"
verify = { modules = ["nvidia", "nvidia_drm"] }
note = "Open kernel modules need kmod-nvidia-open; decided by GPU generation."
```

```toml
# nimbus/catalog/zed.toml
schema = 1
id = "zed"
provider = "artifact"                # the Chezmoi external shape, system scope
url = "https://github.com/zed-industries/zed/releases/download/v0.200.0/zed-linux-x86_64.tar.gz"
sha256 = "<64 hex>"
install_to = "/opt/zed"
link = { "/usr/local/bin/zed" = "/opt/zed/bin/zed" }
```

A component is where the opinion lives.

```toml
# nimbus/components/nvidia.toml
schema = 1
id = "nvidia"
summary = "NVIDIA proprietary stack from RPM Fusion"
requires = ["rpmfusion-nonfree"]
packages = ["akmod-nvidia", "xorg-x11-drv-nvidia-cuda"]

[[files]]
source = "root/etc/modprobe.d/nvidia.conf"
target = "/etc/modprobe.d/nvidia.conf"
on_change = ["dracut"]

[[manual]]
id = "mok-enroll"
when = "facts.secure_boot"
summary = "Import the akmods key with mokutil and enroll it at the next boot."
check = ["mokutil", "--test-key", "/etc/pki/akmods/certs/public_key.der"]

[warnings]
missing_hardware = "No NVIDIA GPU detected; this component installs anyway."
```

```toml
# nimbus/profiles/hyprland-noctalia.toml
schema = 1
id = "hyprland-noctalia"
components = ["wayland-base", "hyprland", "noctalia", "noctalia-greeter",
              "xdg-portals-hyprland", "hyprland-seed-session"]
```

```toml
# machines/desktop.toml  (unchanged shape)
schema = 1
profiles = ["common", "development", "hyprland-noctalia"]
components = ["nvidia", "windows-vm"]
packages = ["ripgrep", "flatpak:org.signal.Signal"]
package_exclusions = []

[package_constraints]
hyprland = ">=0.56, <0.57"

[dotfiles]
repo = "https://github.com/Furyfree/dotfiles.git"
```

Rules that keep resolution boring:

- Profiles list components. Components may `requires` components. Nothing
  imports profiles. Cycles, unknown IDs, and duplicate IDs are errors.
- `when` and `warnings` read facts but never select. A component is either
  in the manifest or not. Detection produces warnings, never membership.
- Provider variants such as open versus proprietary NVIDIA modules are
  chosen inside the selected component from facts, and the choice is shown
  in the plan.
- Triggers are data too: `nimbus/triggers/dracut.toml` holds the argv, the
  privilege, and whether it implies a reboot.

### 3.6 Resolution, facts, and the plan

```text
machines/<id>.toml + nimbus/     ->  resolve   ->  desired graph
read-only inspection             ->  facts     ->  observed state
/var/lib/nimbus/receipts         ->  applied   ->  last-applied state
desired x observed x applied     ->  plan      ->  ordered steps + warnings
```

- `nimbus validate` runs the resolver with no facts. It is the CI check for
  the workstation repository and needs nothing installed but the engine.
- `nimbus facts` prints what inspection found as JSON. It is the debugging
  tool when a plan looks wrong, and its fixtures drive golden plan tests.
- `nimbus plan` is read-only. `--out FILE` writes the canonical plan and its
  digest. `nimbus apply FILE` recomputes and refuses on mismatch. Without a
  file, `apply` plans, shows, asks, and applies in one run, exactly as
  specified today.
- `--target RESOURCE` limits a plan to one resource and its dependencies for
  the "just install this now" case. `--reinstall RESOURCE` forces a
  provider reinstall. Both are printed loudly in the plan header.
- Prune candidates stay informational unless `--prune`. Unchanged.

### 3.7 Execution

Keep every rule in `SPEC.md` about privilege and make the mechanism concrete:

```text
nimbus apply (as you)
  step 1  sudo nimbus __step PLAN_DIGEST 1     dnf install ...     one prompt
  step 2  sudo nimbus __step PLAN_DIGEST 2     write 3 files       reuses ticket
  step 3  sudo nimbus __step PLAN_DIGEST 3     systemctl enable    reuses ticket
  step 4  sudo nimbus __step PLAN_DIGEST 4     dracut trigger
  step 5  sudo nimbus __step PLAN_DIGEST 5     write receipts
  chezmoi init ...                              as you, no sudo
```

- The child process is the same binary. It receives the plan digest and a
  step index, re-reads the plan from `/var/lib/nimbus/plans/<digest>.json`,
  refuses if the digest does not match, and executes exactly one step.
  There is no daemon, no helper, no keepalive. Steps are ordered so
  privileged steps are adjacent and sudo's normal ticket does the rest.
- Each step writes its own receipt atomically before the next step starts,
  so a failure leaves accurate partial state and never a "success" record.
- A receipt records: Nimbus version, checkout commit and dirty flag,
  definitions tree digest, plan digest, resource ID, provider, exact argv,
  verification result, and the recovery point ID when one was taken.
- Before any step classified `disruptive` or `reboot`, Nimbus takes a
  recovery point: read-only Btrfs snapshots of `root` and, when Flatpaks
  change, `flatpak`, plus a `/boot` and `/boot/efi` archive when kernel or
  boot files change. The layout in `FEDORA_TEST_INSTALLATION.md` already
  defines the subvolumes and exclusions. Rollback is documented manual work
  first; `nimbus rollback ID` arrives only after the restore procedure has
  been tested in the VM.

### 3.8 Files, triggers, and the seed session

The `file` provider is Chezmoi's idea applied above the sudo line:

- The source tree under `nimbus/root/` mirrors the target path. Mode and
  owner default to `0644 root:root`; a component overrides them explicitly.
- `nimbus diff` shows the file changes a plan would make, the way
  `chezmoi diff` does.
- Files adjacent to `.rpmnew` or `.rpmsave` are reported by `doctor` and
  never merged.
- `on_change` names triggers. A trigger runs at most once per apply, after
  every file that named it, like `run_onchange_` scripts with a shared hash.

The seed session replaces the `$HOME` seed file:

```text
/usr/share/wayland-sessions/hyprland-seed.desktop
    Exec=Hyprland --config /usr/share/nimbus/seed/hyprland.lua
/usr/share/nimbus/seed/hyprland.lua
    minimal keybinds, exec-once noctalia --daemon, a terminal
```

The greeter shows "Hyprland (Nimbus seed)" next to the normal "Hyprland"
entry. On first login before `chezmoi apply` the seed works. After
`chezmoi apply` the normal entry works and the seed stays as a recovery
session for the day a user config breaks. No yield logic, no path check, no
user file.

### 3.9 Updates and constraints

Fedora updates packages; Nimbus decides what may move.

- `package_constraints` are materialized into `dnf versionlock` as a normal
  planned resource. Removing a constraint from the manifest plans the
  unlock. Anyone running `dnf upgrade` or `topgrade` then respects the same
  policy Nimbus resolved. A constraint that is not materialized is rejected
  by `validate` until the provider supports it.
- `nimbus plan --upgrade` includes available updates for managed packages as
  steps, grouped by `update_group`. The `desktop-session` group becomes one
  `dnf` transaction preceded by a recovery point and followed by a
  logout-or-reboot note. Its membership is a catalog question and stays in
  `OPEN_QUESTIONS.md`.
- Daily `topgrade` stays allowed and stays Chezmoi-configured. It is a user
  running native tools, which the design promises to keep working.

### 3.10 The handoff to Chezmoi

Terraform calls this an output. Keep it exactly as small as an output.

```sh
chezmoi init \
  --promptMultichoice 'Profiles=common/development/hyprland-noctalia' \
  --promptString 'Machine=desktop' \
  https://github.com/Furyfree/dotfiles.git
```

- `Profiles` is the resolved profile list, unchanged from the manifest.
  The mechanism in `PROFILES.md` stays.
- `Machine` is new. It is the manifest ID, nothing more. Chezmoi records it
  in its own config through `promptStringOnce`. Templates then read
  `.chezmoidata/machines.toml` for the user-side facts of that machine:

```toml
# home/.chezmoidata/machines.toml
[machines.desktop]
monitors = ["DP-1,3440x1440@144,0x0,1"]
[machines.laptop]
monitors = ["eDP-1,preferred,auto,1"]
```

  No typed-variable schema in Nimbus, no second data path, and a direct
  `chezmoi init --prompt` on a MacBook simply answers the prompt or leaves
  it empty.
- Hardware facts do not cross the handoff. Chezmoi templates can run
  `lookPath` and `output` themselves when a user file truly depends on
  hardware.
- The contract test: `nimbus validate --chezmoi-template
  home/.chezmoi.toml.tmpl` parses `$machineChoices` and fails when the set
  differs from `nimbus/profiles/*.toml`. It runs in the workstation
  repository CI next to `chezmoi execute-template`.
- Nimbus never runs `chezmoi apply`, never synchronizes Git, and never reads
  Chezmoi's config back. Unchanged.

### 3.11 What changes on the dotfiles side

Small, and all Chezmoi-native:

1. Add the `Machine` prompt to `.chezmoi.toml.tmpl` and a
   `.chezmoidata/machines.toml` with the two current machines.
2. Add `nimbus/` at the checkout root and a CI job that runs
   `nimbus validate` and the template contract test.
3. Make `~/.config/mise/config.toml` the single declaration of user-scope
   tools, including `cargo:`, `npm:`, `pipx:`, and `go:` backends. Allow one
   `run_onchange_after_mise-install.sh.tmpl` that hashes that file and runs
   `mise install`. This is a user action on user files and fits the
   existing script rule; note the exception in `AGENTS.md`.
4. Keep everything else in `ROADMAP.md` as is: Zsh first, Bash second,
   shared applications, platform files, desktop, 1Password.

### 3.12 One bootstrap flow

```text
fresh Fedora 44 Everything, user in wheel
  |
  |  sudo dnf copr enable <owner>/nimbus && sudo dnf install nimbus
  |  (others: download the release binary and verify its checksum)
  v
nimbus init [REPO] [--machine ID]
  1. check Fedora 44, x86_64, not root, no existing Nimbus config
  2. obtain the checkout at ~/.local/share/chezmoi
       REPO given          -> one git clone, working tree untouched
       no REPO             -> nimbus init --new writes the example tree
                              and runs git init; origin is added later
  3. choose the machine
       machines/<ID>.toml exists -> load, validate, never rewrite
       otherwise                 -> select profiles, components, packages;
                                    review the new manifest; write it
  4. write ~/.config/nimbus/config.toml
       checkout = "/home/pby/.local/share/chezmoi"
       machine  = "desktop"
  5. plan; review; apply (installs chezmoi and git if missing)
  6. chezmoi init with the handoff, no apply
  7. print the next commands: chezmoi diff, chezmoi apply, git status
```

Fresh, reinstall, and no-repository are now the same flow. The only
difference is step 2, and the "adopt into a repository later" story is
`git remote add origin` plus `git push`, which is plain Git work the user
already owns.

The config file replaces the symlink. Two explicit keys are easier to
inspect, print in `--json`, and override with `--checkout` and `--machine`
than a link whose target may dangle. `~/.config/nimbus/machine.toml` as a
plain local manifest disappears with the no-repository flow.

### 3.13 The daily loop

```text
check    nimbus status                chezmoi status
change   edit nimbus/ or machines/    edit home/ (chezmoi edit)
preview  nimbus plan                  chezmoi diff
apply    nimbus apply                 chezmoi apply
share    git commit && git push       (same repository)
sync     chezmoi update --apply=false     pulls both halves
         nimbus status                    "definitions changed, run plan"
         nimbus plan && nimbus apply
         chezmoi diff && chezmoi apply
update   topgrade                          honors versionlock
         nimbus plan --upgrade             for grouped desktop updates
```

`nimbus status` compares the definitions tree digest in the last receipt
with the checkout. That answers "is there unapplied config" instantly, with
no inspection, the way Terraform notices a config change before a refresh.

### 3.14 Usable by others

What is generic after this design: the engine, the providers, the schemas,
the verbs, the handoff contract, and the example tree. What is personal: the
workstation repository, the COPR, and the Fedora 44 test matrix.

Another person starts with `nimbus init --new`, edits `nimbus/` and
`machines/`, and pushes it wherever they like. They never touch Go. That is
the same promise Terraform and Chezmoi make.

First-iteration limits, stated plainly in `README.md`:

- Fedora 44 on x86_64 only, tested on two machines.
- Providers: `dnf`, `copr`, `flatpak` (system), `file`, `systemd`,
  `artifact`. No boot provider until phase 6.
- One desktop profile is maintained. Others are reserved names.
- No TUI. Every command has `--json`; a TUI is a later view over that.

## 4. Command surface

Engine verbs only. Everything that was a personal convenience moves out.

| Command | Reads | Writes | Notes |
|---|---|---|---|
| `nimbus init [REPO] [--machine ID] [--new]` | checkout | config, manifest, clone | section 3.12 |
| `nimbus validate [--chezmoi-template F]` | definitions | nothing | CI check |
| `nimbus config resolve` | definitions | nothing | desired graph, `--json` |
| `nimbus facts` | system | nothing | inspection as JSON |
| `nimbus status` | all three states | nothing | quick drift and pending work |
| `nimbus plan [--out F] [--upgrade] [--target R] [--prune]` | all three | nothing | |
| `nimbus diff` | plan | nothing | file changes only |
| `nimbus apply [F] [--prune] [--target R] [--reinstall R]` | plan | system, receipts | section 3.7 |
| `nimbus managed`, `nimbus unmanaged` | receipts, facts | nothing | Chezmoi verbs |
| `nimbus why RESOURCE` | desired graph, receipts | nothing | |
| `nimbus forget RESOURCE` | receipts | receipts | stop managing without removal; later |
| `nimbus doctor [--explain]` | system | nothing | includes `.rpmnew`, quarantined providers |
| `nimbus packages add|remove|list` | manifest | manifest | edits the manifest, then says "run plan" |
| `nimbus version` | | | prints supported definitions schema range |

Moved out:

- `windows start|stop|connect|purge-data` become a script in `home/` or a
  systemd unit and `xfreerdp` alias. Nimbus keeps the `windows-vm`
  component: packages, KVM group, pinned image, unit, loopback binds.
- `launch browser|webapp` become a small script in `home/`. Key bindings
  live in Chezmoi already.
- `postinstall` becomes a section of `nimbus status`, derived from
  components' `[[manual]]` entries and their `check` commands. A separate
  interactive command can come later if the list grows.
- The dashboard waits until every verb above has a stable `--json`.

## 5. Invariants

Each of these is a test, a linter, or a CI job, not a sentence in a doc.

1. Nimbus writes under `$HOME` only in `~/.config/nimbus` and
   `~/.cache/nimbus`. A test runs every command in a sandbox home and
   asserts no other path changed.
2. Read-only commands never call `sudo`, never open a network socket, and
   never write. The fake runner records every exec and the test fails on
   any mutating argv.
3. Every receipt contains a Nimbus version, checkout commit, definitions
   digest, plan digest, and verification result. Schema-validated on write
   and on read.
4. `nimbus validate` passes on the workstation repository in CI, and the
   template contract test proves the profile set matches.
5. Removing the `nimbus` package leaves `chezmoi` fully working. Removing
   `chezmoi` leaves the system booting into the seed session. Both are VM
   tests.
6. No Go source contains a package name in a branch. A grep in `just check`
   fails on `== "zed"` and friends.
7. A plan digest mismatch at apply time is a hard refusal, tested by editing
   the manifest between `plan --out` and `apply`.
8. Every mutating provider has a fixture proving a failed native command
   produces no "applied" receipt.

## 7. What Nimbus and Chezmoi promise each other

- Nimbus runs before Chezmoi on a fresh machine and never depends on
  Chezmoi afterwards.
- Chezmoi never depends on Nimbus. Its only Nimbus-shaped inputs are two
  prompt answers that a human can type.
- Neither reads the other's state. Nimbus does not parse Chezmoi's config;
  Chezmoi does not read `/var/lib/nimbus`.
- Both read one repository and one manifest ID. The machine ID is the only
  shared identifier and it is spelled once, in a file name.
- Nimbus installs the tools that Chezmoi-managed files configure: shells,
  editors, `mise`, `1password`, Hyprland. Chezmoi never declares a package.
- A user can `git clone`, run `chezmoi init --prompt`, and get a working
  home on any OS. A user can run `nimbus plan` on a machine with no home
  files applied and get a correct system. Nothing is coupled that does not
  need to be.

## 8. Decisions this design revisits

| Today | Proposed | Why |
|---|---|---|
| definitions embedded in the binary; changes need a release | definitions in the workstation repo; receipts record the commit | iteration speed, usable by others, one sync path with Chezmoi |
| `~/.config/nimbus/machine.toml` symlink to the manifest | `~/.config/nimbus/config.toml` with `checkout` and `machine` | explicit, printable, overridable, no dangling link |
| no-repository flow writes a plain local manifest | `nimbus init --new` creates a local repository | three flows become one |
| the only Git read is the init clone | plus read-only `rev-parse HEAD` and `status --porcelain` for receipts | provenance; still no fetch, commit, or push |
| Mise, Cargo, uv providers in Nimbus | user-scope tools via `mise`, declared in a Chezmoi file | one owner per intent; smaller engine |
| seed `hyprland.lua` written into `$HOME` with yield logic | system-owned seed session entry using `Hyprland --config` | no `$HOME` writes; doubles as a recovery session |
| profile handoff only | profile handoff plus `Machine=<id>` | unlocks `.chezmoidata` per machine with no Nimbus schema |
| `package_constraints` resolved only inside Nimbus | materialized as `dnf versionlock` resources | constraints must survive `topgrade` |
| catalog entry per package | catalog as exception list; bare names mean `dnf` | far fewer files, same guarantees |
| Bubble Tea dashboard, package browser, `windows`, `launch` in the engine | engine verbs only; conveniences move to `home/` | scope, and personal versus generic |
| `postinstall` as its own interactive command | `[[manual]]` entries surfaced by `status` | same information, no new UI yet |
| recovery points mentioned only for `desktop-session` | recovery point before any disruptive step, ID in the receipt | the Btrfs layout already exists for this |
| bootstrap adopts Nimbus, Chezmoi, Git specially | Chezmoi and Git are ordinary `common` catalog entries; Nimbus's own package is in the owner's `common` and absent from others' | removes a special case |

Things this design does not change: the ownership split, plan before apply,
receipts, the digest guard, prune semantics, no daemon, no keepalive, no
`chezmoi apply`, no silent Git, Fedora 44 first, Cobra and `go-toml/v2`,
read-only phase 1, and the 1Password design in the dotfiles roadmap.
